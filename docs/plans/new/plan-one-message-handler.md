# Replace channels with one message handler

## Overview

Today an app gives Ziggy's core a table of channels (`AppHandlers.channels`, a list of `ChannelEntry` name and handler pairs) and a table of task channels (`AppHandlers.task_channels`), and every UI message carries a `channel` name that the core routes on. This plan removes channels. The app gives the core one Zig function, `handle_message`, that receives every message the UI sends and does what it likes with the payload, and the UI sends and listens without naming a channel. Ziggy's own messages and events (tasks, the platform, menus, dropped files, the test hooks) stay inside Ziggy and get their own calls on `window.ziggy`, so an app never sees them in its handler. The change is made in Ziggy first and tested against the two example apps on a local checkout, then released as a new version tag once the human approves, then taken by the examples from that tag, then by Photosphere.

### Phase 10: app messages and system messages

20. [ ] The human wants two separate, isolated kinds of message: app messages, for app developers, and system messages, for Ziggy itself. An app never sees a system message and cannot send or define one, and Ziggy's own code never goes through the app's handler. Today they are already apart in routing (a `ziggy` field sends a message to Ziggy's own table in `core.zig`), but they share one envelope, one entry point (`Core.postMessage`) and one `window.ziggy` object. This step makes the split explicit end to end, while keeping one route from each native app into the core so no native bridge is added.
   - **Wire format.** Every message from the UI carries a `kind` of `"app"` or `"system"`: `{kind: "app", id, name, data}` and `{kind: "system", id, name, data}`. Every event from the core does the same: `{kind: "app", data}` from `core.sendEvent` and `{kind: "system", name, data}` for Ziggy's own (task messages, task completed, menu actions, core errors, test commands). The `ziggy` field goes. A message with no `kind`, or another value, is refused as `InvalidMessage` and reported as a `core-error` system event. Write the format down in the comment block at the top of `packages/ziggy/core/src/lib/ziggy-inject.js` and in `docs/development/architecture.md`.
